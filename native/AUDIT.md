# Native port audit

Method: every catalogue course launched headless in release (`JUMPMAN_COURSE=<id> JUMPMAN_SCREENSHOT=... JUMPMAN_EXIT_AFTER=7`, Mario skin, audio off), logs grepped for panic/warn/error (none), screenshots read for black screens, missing geometry/actors, scale, sky/fog/water, HUD. Then every act (`JUMPMAN_ACT`) and every `warpSpawns` entry (`JUMPMAN_ENTRY`) of the Mario courses (147 runs, all clean), castle_inside areas 2 and 3, the 8 experiments, scripted playthroughs (teleport to the star -> dance -> iris wipe -> castle -> save dialog -> save; castle door; painting -> act selector -> course), and a frame-time pass (`JUMPMAN_FPS=1 JUMPMAN_NOVSYNC=1`).

## Defects found and fixed
| Defect | Root cause | Fix |
|--------|-----------|-----|
| After ANY course switch (star exit, door, painting, death warp to another course) Mario, the whole HUD, wipes and menus disappeared | `progress::tag_new` tagged every entity spawned between `mark_entities` and `tag_course_entities` as `CourseScoped`; unordered Startup systems (HUD, Mario view, camera, overlays, dialog UI, shell, audio, ...) landed in that window and were despawned by the first switch | `progress::PersistentSpawn` system set; all persistent Startup spawners are in it and `mark_entities` runs after it |
| Water surfaces vanished after a switch | spawned in Startup, tagged course-scoped, never rebuilt | `fx/water.rs` registers a `CourseRebuild` hook |
| Playground: star dance fires at the start (star sat on Mario's spawn and was ready immediately) | no `starLocations` entry, `requireCoins` not modelled | star at the TS position, gated on all meadow coins (`flow.rs`) |
| HUD title stayed on the previous course | the HUD swaps the curly apostrophe, the switch compared the raw name | compare normalised titles |

Test hooks added: `JUMPMAN_DEBUG_LOG=n` also logs `FLOW a -> b` transitions and the flow in the Mario line, `JUMPMAN_NOVSYNC=1`, `JUMPMAN_MSAA=off|2`.

## App-layer parity (moving platforms, colliders, goombas, cannons, doors, coins, signs)
`tests/rustFixtures.game.gen.test.ts` + `native/src/game/game_tests.rs` (see PORTING.md) replay the real TS world factory against the Rust app layer for 38 course/act/area runs x 2400 frames, seven bit-exact state hashes per frame. It found and fixed in Rust (full list in PORTING.md): three.js matrix math for platform collision, platform timer RNG order, collider sync timing and run-time colliders (chain chomp post), invincibility / coin pickup / loot coin order, goomba loot coin timing, cannon and buddy ordering and seat state, signpost floor snapping, the missing Jolly Roger Bay ship collision, missing castle entrance door and DDD warp wall colliders, wf implied collision models, JRB/DDD area-2 spawns, world freezing during door cutscenes. Not compared (presentation): particles, spark x/z jitter (own RNG); sound triggers are compared separately (see Sound cue parity).

### Second app-layer differential (`tests/rustFixtures.game2.gen.test.ts` + `native/src/game/game2_tests.rs`)
King Bob-omb dialog (ids 17/116/128, with the NpcDialogCamera eye/focus/return transition every frame), Koopa the Quick accept/decline, racing penguin accept/decline, the Wing Cap switch (collider squash, world surface hash, wing boxes), `CoinEffects` (number bounce, burst cadence, spark frames/scale), fading warps (bob pads) and in-place instant warps (castle_inside area 2): all bit-exact. Found and fixed in Rust: (1) `Math.hypot` vs libm `hypot` (and the 3-argument hypot in `polar`) in the camera, doors, paintings, fading-warp code -> `js_hypot`/`js_hypot3`; (2) NpcDialogCamera focus lerp used glam's rounding instead of three's `x += (v-x)*a`; (3) the king camera's return tail started one tick early and was dropped one tick late; (4) the racing penguin question skipped platforms/goombas/coin/invincibility steps (the whole tick was replaced) and Mario was stepped on the tick Koopa's invitation/result dialog opened (`Game.stepWorld` returns before Mario's step): both now live in `GameSim::tick_with` (`race_hold`), Koopa's top-of-tick question is `GameSim::koopa_question`; (5) a racer `answer` var was written every tick (extra object var); (6) fading warp ignored `ACT_TELEPORT_FADE_OUT` without an armed pad (TS falls through) and never snapped the camera behind Mario at the destination (`Progress::rig_snap`).

## Audio parity (`tests/rustFixtures.audio.gen.test.ts` + `native/src/audio/audio_tests.rs`)
The real `Sfx.ts` runs in node against a fake worklet node that records every port message; the messages are turned into engine calls (`music-worklet.js` logic) and rendered through the same `sm64-us.wasm` in V8 at the engine's 32 kHz, commands applied between render blocks (`tests/audioScenes.json`: 7 scenes x 8 s - Bob-omb / Cool Cool / castle music with location changes, jump/land/coin/double+triple jump/footstep/star/red coin/secret/1up/bonk/ground pound/explosion sfx, underwater Jolly Roger Bay with swim/splash/water coin, metal cap + power music + cap switch, king/race/clear music events). The Rust `Sfx` + `Processor` (wasmi) plays the same scenes. Result (`cargo test -p jumpman audio_matches -- --nocapture`): the engine-call streams (name, arguments, render-frame stamp) are identical in every scene and the 32 kHz PCM is sample-for-sample identical (100.00%; RMS, Pearson correlation 1.000000, spectral cosine 1.000000 in all 7). So the Sfx port, `courses.json`/`sounds.json` lookups, terrain/metal/underwater offsets and the wasmi interpreter agree bit-for-bit with V8. Trigger parity is covered by the next section; not covered: the device-rate resampling (needs a real output device). The render thread's stack was raised from 64 to 256 MB: a debug build of the interpreter overflowed 64 MB on the `sound_effect` scenes.

## Warp parity (`tests/rustFixtures.warps.gen.test.ts` + `native/src/game/warps_tests.rs`)
Drives the real TS world factory (`prepareCourse`, `MarioRuntime`, object manager) with copies of the `Game.ts` warp blocks and compares, as readable strings or per-frame state hashes: (1) the resolution of every warp object, every castle/course door (pull and push), every castle painting floor (each `SURFACE_PAINTING_WARP` type of the three castle areas, at height 0 and 80, including the warp-object that fires first) and every death / fall / floor warp of every course json (what is asked of `loadCourse`, `changeLinkedArea` or the act selector: course, entry, push, act, area); (2) death and fall warps on the real tick (Mario dying, falling below `deathHeight`, falling onto the totwc death plane, 0 lives = game over), the tick on which the load is requested and the carried health / counters; (3) the jrb sunken-ship floor warp (20 ticks while Mario keeps simulating, carry, load tick); (4) the area-changing instant warps (ddd both ways with `changeLinkedArea`, wdw, castle_inside area 2) for 360 frames x 5 hashes; (5) the arrival state (spawn + 60 scripted frames of Mario / objects / world surfaces) for each of the 64 distinct (course, entry, push, act, area) targets those warps can load. 228 comparisons (161 resolutions, 67 hashed scenarios), all bit-exact. Found and fixed in Rust: (1) same-course door / warp / instant-warp area changes went through the linked-area hot swap for every course, but only ddd and ccm have a linked area in the web build (`prepareCourse`): castle_inside doors to areas 2/3 are plain course loads (new Mario, restart), and wdw's instant warp to area 2 is a no-op (Rust tried to load a `wdw.2.json` that does not exist); (2) `begin_warp` passed a warp object's area into the act selector / loader although `Game.ts` only uses it for the linked swap (`loadCourse(dest, entry)` -> area 1); (3) the death / fall wipe loaded one tick early (the Closing wipe advanced in the same post-tick that started it); (4) the jrb floor warp froze Mario for the 20-tick iris and loaded 2 ticks late - the web build keeps simulating Mario (health drain etc. is part of the carried state) and loads on the 20th counted tick; the totwc floor warp now freezes the world like `stepWorld`'s early return; (5) a queued load now stops the sim (`loadingCourse`). Not reachable / not compared: the jrb `0x32` floor is never a movement floor in the exported collision (the pit falls out of the world and takes the fall warp), so that test forces the type on the spawn floor; the totwc death-plane floor warp is shadowed by the fall warp (the void check fires in Mario's step first) and only runs when no death hook exists (experiments), so only its freeze/timer code is shared with the verified jrb path. The door cutscene itself and the act selector UI are covered by the first/second app-layer differentials and unit tests.

## Sound cue parity (`tests/rustFixtures.cues.gen.test.ts` + `native/src/audio/cue_tests.rs`)
`Game.ts` cannot run in node (WebGL renderer, DOM), so the cue differential replays every event kind through a literal copy of the sfx lines of `processEvents` / `processObjectEvents` / the progression glue with the real `Sfx.ts` and a recording music node, and through the Rust functions the Bevy systems call (`audio::dispatch_sim_event`, `audio::apply_cue`, split out of `react_to_sim` / `apply_cues`) with a Rust `Sfx`: 142 cases (39 Mario batches covering every event kind incl. the land + ground-pound-land suppression and jump variants, 49 object events with every phase/cue/flag - waterBomb phases incl. the silent `burst`, break wall left/right, snowman/racer/koopa cues, the race outcomes, king dialog ids, Bowser/Big Bully/Whomp King/Big Boo defeats - and 54 progression cues: star, star sound, teleport, cap switch, death warp, coin dry/underwater, signs read/open/page/close, course coin, secret, red coin, spawned/coordinate star, cannon door, lift cues, menu sounds, Peach voices, music events). Engine-call streams (`sound_effect` ids/variants/positions, `music_*`) are identical in all 142; no Rust change was needed. The frame on which a cue fires is the frame on which the event fires: the events come from the sim (differentially tested) and `hud_tick`/coin ticking mirrors `Game.stepWorld`. Not covered headlessly: cues that only exist inside `Game.ts` flows that need the browser (star dance / result screen sequencing and the ending cutscene timing are verified by reading plus the Rust-only flow tests in `progress/flow.rs`), and the web build's Zelda scenes play no sound beyond the coin cue (so the Rust Zelda module's lack of chest / dialogue / nut / Gohma sounds is parity, not a gap).

## Visual verification (headless screenshots, release build)
Checked by reading the PNGs: controls screen idle / listening ("PRESS A KEY...") / Esc-cancel (stays on the controls screen, binding unchanged: the cancelling key is swallowed from menu navigation) / rebind to K (Jump = K, the old K binding on Crouch is stolen); course result (`JUMPMAN_FLOW=result`) and act selector (`selector`) in the SM64 bitmap font; HUD (lives/coins/stars/title in the HUD font); secret/red-coin numbers (`JUMPMAN_FX_NUMBER=4`); the Zora's River water (`scrollT`: the water region changes between shots 0.5 s apart, the ground does not). New hooks: `JUMPMAN_SHELL_SCRIPT` accepts `rebind:<action>` and `key:Escape|Enter|Space|KeyJ|KeyK|KeyF` (real `KeyboardInput` events), `JUMPMAN_FX_NUMBER=<n>`. Defects found and fixed: the game-over card was invisible (the last Circle wipe frame, z 60, painted black over the card's text, z 50); the secret/red-coin number and spark models cast sun shadows onto the ground (in the web build only the player characters have `castShadow`).

## Performance
Release, 2080x1360 window, uncapped, shared machine (other jobs were using the GPU, so numbers are noisy): 11-19 ms/frame; the heaviest are the large SM64 outdoor levels (bob, castle_grounds, wf, bbh ~18.6 ms) versus 11-13 ms for small courses. Turning shadows off did not change bob; MSAA off gave ~14 ms in one noisy run, so cost is dominated by fill/MSAA at native resolution rather than CPU. No CPU hot spot was found; the 240p/480p render-target scaling in `PORTING.md` would be the lever if more headroom is wanted.
